What type of device or workload a `this-site` resource is — TAPPaaS's `kind`.

---

## Context

ADR-012 Appendix A carries a six-value taxonomy — `node` · `standalone` · `satellite` · `external` · `remote` · `rogue` — marked *"companion reference, not a decision"*, destined for its own ADR. This is that ADR, together with [ADR-022a](<ADR-022a - Administrative Domain.md>) D6/D7, which now owns the "who administers it" half of the split this ADR originally proposed.

Appendix A's table is correct but flat: it answers two questions at once (who runs it, and what type it is), which is why `external` ends up spanning cases that behave differently and why `shim` sits as a peer value beside placements rather than as a state of one. [ADR-022a](<ADR-022a - Administrative Domain.md>) D6 answers the first question; this ADR answers the second.

This is urgent rather than tidy for two reasons:

1. **`kind` is already broken.** `module-fields.json` defines `kind: external-host` as *"a non-module **cluster guest**"*; `satellite-fields.json` defines the same value as *"an EXTERNAL host, **NOT** a Proxmox cluster:vm"*. Both on `main`. A satellite this Site provisions and manages is filed under a value named "external".

2. **`kind` is not just vocabulary — it is a dispatch key.** [ADR-007f](<ADR-007f - Realization.md>) already establishes Manager → Controller → Service as the built control plane: a Manager owns a domain's verb surface (`list`/`show`/`validate`/`reconcile`, …) and calls a Controller for the live I/O behind it. `kind` is the field a Manager would read to pick the right Controller — today `module-manager` does not yet do this (per ADR-007f's as-built mapping it always uses the `cluster:vm` / `network:proxy` install-service hooks regardless of `kind`), but a `proxmox-controller` already exists to be routed to for VM/LXC workloads, and nothing exists yet for a bare hardware device (2026-09-11 sync). A wrong or ambiguous `kind` is therefore not a documentation defect, it is a routing defect. Whether `kind` should let a Manager ask every device the *same* questions (full abstraction) or only enough to route to the right Controller (which then asks its own type-specific questions) is itself still open, direction agreed, mechanism not designed — see Open questions.

## Decision

### 1. `kind` answers one question: what type of device/workload is this

Asked only once [ADR-022a](<ADR-022a - Administrative Domain.md>) D6 has classified a workload as `this-site`. This is `kind` — the object-type marker [ADR-022c](<ADR-022c - Node and Host.md>) D5 defines as tooling-written, never hand-authored. v0.1 asked "what does it run on," which is the wrong question: as `kind` grows beyond VM/LXC (below), two workloads can share a substrate and still be different device types, and the substrate question is already answered elsewhere — by the Host/`node` relationship (ADR-022c), not by `kind`. `kind` answers **what class of device or workload this is**.

**Atomic vs. composite kind — two different registers, two tables, not one.** Five of the six decided values each classify *one* workload or device. `cluster` classifies a *system built from binding several `host`-kind Nodes together* — it has members, the others don't. Concatenating it into a single flat table understates that difference; it gets its own table below, sized for one row today because only one composite value is decided, with room to grow (`kubernetes`, if it's ever ratified, would join it).

**Decided values — atomic kinds** (each classifies exactly one workload or device):

| `kind` | Meaning | Module boundary | Normative anchor | Examples |
|---|---|---|---|---|
| `vm` | a virtual machine (KVM/QEMU) running on a cluster member | the VM | [DMTF Redfish](https://www.dmtf.org/standards/redfish) `SystemType: Virtual`, sub-split by Proxmox VE's own `qemu` API | `openwebui` (App VM in a Service zone) |
| `lxc` | a Linux Container (LXC) running on a cluster member | the container | Redfish `SystemType: Virtual`, sub-split by Proxmox VE's own `lxc` API | `vllm-amd` (declares `dependsOn: cluster:lxc`) |
| `host` | its own Node, manageable by TAPPaaS (SSH, checks, updates) but not a cluster guest — cluster-member or not | the host | Redfish `SystemType: Physical` | `backup` (PBS, non-cluster-member) · `tappaas1`/`tappaas2` (cluster-member Proxmox nodes — same `kind`; membership is recorded separately, §2 below) |
| `device` | reachable by IP, unmanaged beyond network configuration — TAPPaaS cannot SSH into it or run checks against it | the device itself (no VM/host distinction applies) | [ArchiMate 3.x](https://pubs.opengroup.org/architecture/archimate3-doc/ch-Technology-Layer.html) Device ("a physical IT resource with processing capability... can also be used to model virtualized hardware") — the same term ADR-022c D1 already reaches for | 12 of the 21 real modules in the Community repo (57%) — `alfen`, `hue`, `sonos`, `smlight`, `sysap`, `shelly-fleet`, `reolink`, `samsung-tv`, `solaredge`, `wiim-fleet`, `irrigation`, `synology` — every one policy-only (`network:rules`/`network:discovery`/`network:snat`, never `cluster:vm`/`cluster:lxc`), none `kind`-tagged today |
| `oci` | an OCI application container — never a peer substrate on its own; always runs nested inside a `vm`/`lxc`/`host` | *nested — exactly how an `oci`-kind module declares that nesting is undesigned; deferred on the same terms as `cluster`'s membership mechanism, see Open questions* | [OCI Image & Runtime Specifications](https://opencontainers.org/) — distinct from `lxc`: LXC is a system container (own init, full OS surface), OCI/Docker is an application container (one process, shares the host kernel more directly) | `ollama-nvidia` — `kind: lxc` at the substrate level, its `.meta.json` pins a Docker image (`ollama/ollama:0.32.2`) run via `docker-compose.yml` *inside* that LXC |

**Decided values — composite kinds** (a value whose module has *members*, each itself atomic-`kind`):

| `kind` | Meaning | Module boundary | Normative anchor | Examples |
|---|---|---|---|---|
| `cluster` | the Proxmox cluster itself, as a module in its own right — `site.json` stops directly enumerating cluster nodes; its members are `host`-kind Nodes | the cluster | Redfish `SystemType: Composed` ("a computer system constructed by binding resource blocks together"); ArchiMate's **Composition** relationship for the `cluster`–`host` membership itself (see below) | `src/foundation/cluster/cluster.json` — the catalog module **already exists** (`status: Production`, `provides: ["vm","lxc","ha"]`); it has simply never carried a `kind` value, same as everything else in the repo |

`cluster` and `device` are decided-now, not future/3.0 items: neither requires the `node`→`depends-on` change (see the parking lot below) — `cluster` only needs a module file of its own, and `device` only needs a module registered against a thing that isn't a Node TAPPaaS can inspect.

**Why `cluster` is a composite, precisely — the same two normative anchors already in use, used more precisely:**

- **ArchiMate's Composition relationship**: *"the concept may only be part of one group"* — a Proxmox node belongs to exactly one cluster at a time, which is Composition, not Aggregation (which permits sharing across groups). `cluster`–`host` is a Composition relationship between two ArchiMate Node-family elements.
- **DMTF Redfish's Composability model**: a `ResourceBlock` (atomic) is bound, via the Composition Service, into a `ComposedNode` (the `SystemType: Composed` value already cited) — the same shape as individual hosts bound into a cluster.

Naming this makes `kubernetes`'s blocking question sharper, not just parked: *"is a K8s deployment one module or a grouping of modules"* is exactly *"is `kubernetes` also a composite kind, belonging in this second table"* — the same question this ADR just answered for `cluster`. It does not resolve `kubernetes` (what its members would be — pods, nodes, both — is still undesigned), but it means a future pass has a named category and a table to slot it into rather than re-deriving the question from scratch.

**This does not pull the `depends-on`/3.0 work forward.** `cluster` being decided-now (above) only requires a module file to exist for the cluster; *formally declaring* its composition (the cluster module's `dependsOn` naming each member host, per the recursive-module model) is exactly the parking-lot item below. The category and its table are decided now; the mechanism that fully realizes membership is not.

**MECE check.** Four atomic values plus one composite value, five pairwise boundaries, each on a different axis and none overlapping:

- **`vm` vs `lxc`** — both are cluster guests; the axis is which Proxmox API manages them (`qemu` vs `lxc`), not a fuzzy distinction.
- **`host` vs `device` — the one worth spelling out, since both entries can be "a physical thing with an IP."** The axis is **manageability, not physicality**. A `host` can be virtual too (the ADR-010 satellite, a cloud VPS TAPPaaS treats as its own Node) — what makes it `host` is that TAPPaaS can inspect and manage it like any Debian machine. A `device` happens to be physical in every case raised so far, but that's incidental: what makes it `device` is that TAPPaaS can configure network reachability to it and nothing more. The Meaning column above now leads with that discriminator rather than "physical," so the two rows don't read as overlapping on first pass.
- **`host` vs `cluster` — atomic vs. composite, the two tables' own boundary.** An individual Node versus a Composition of several Nodes; disjoint by construction — a `cluster` value never applies to a single machine, and a `host` value never applies to the aggregate.
- **`device` vs everything else** — a `device` never runs a TAPPaaS-managed workload, so it cannot collide with `vm`/`lxc` (which do) or `host`/`cluster` (which TAPPaaS administers directly); it is the one value for things TAPPaaS only sees on the network.
- **`device` vs ADR-008's network-plane hardware — a boundary this ADR should state, not leave implicit.** `device` covers IoT/energy/entertainment appliances (the examples above). Physical network infrastructure — switches, APs — is a different domain, already owned by `switch-controller`/`ap-controller` under the `network` Stack (ADR-007f, ADR-008); those are never modeled as `kind`-classified modules at all, `device` or otherwise. A UniFi controller itself (`unifi`/`unifi-os`) is `kind: vm` — it's TAPPaaS-managed software; the physical switches/APs it controls are outside this taxonomy entirely, by domain, not by a `kind` value. Confirmed by inspection: no module in either repo blurs this line today.
- **Positive proof this splits on the right axis.** `deconz` (core, `kind: vm` — a VM with USB passthrough to a physical Zigbee dongle) and `smlight` (Community, `kind: device` — a network-attached Zigbee coordinator, policy-only) are the same *application domain* (Zigbee) and land on different `kind` values, correctly: the taxonomy asks "is there TAPPaaS-managed compute," not "what does it do."

**Why `vm`/`lxc`, not `guest`.** v0.1–v0.4 used `guest` (a VM or LXC on a cluster member) as one value, retired on review: it is ambiguous in exactly the way `external-host` was — a Kubernetes pod is colloquially a "guest" too, so the name does not distinguish anything. The replacement follows the same principle as every other decided value here: name it after what actually differs operationally. A Manager's `module-manager list` already does different work for a Proxmox VM than for an LXC container, so collapsing the two back into one value would re-hide the exact difference §Context 2 exists to expose.

**Normative anchor.** [DMTF Redfish](https://www.dmtf.org/standards/redfish) `ComputerSystem.SystemType` (verified against the current schema) gives the top-level split the table above sits inside: `Physical`, `Virtual`, and `Composed`. Redfish does not distinguish hypervisor VMs from containers within `Virtual`, and has no notion of an uninspectable network appliance at all (its whole model assumes something addressable as a `ComputerSystem`) — both gaps are filled from sources closer to what TAPPaaS actually runs: Proxmox VE's own API (`qemu` vs `lxc` endpoints) for the guest sub-split, and ArchiMate's Device element — already cited in this ADR family's normative-sources table — for the uninspectable case.

**`external-host` is retired.** It named the administrative aspect (now [ADR-022a](<ADR-022a - Administrative Domain.md>) D6) while defining the hosting one, which is why its two schema definitions contradict each other.

**Proposed — not decided, and now sharper than "undesigned":**

`kubernetes` is not one open candidate, it's a name that turns out to cover **two different composites**, conflated exactly the way `external-host` once conflated two meanings in one value — decomposing this, not force-picking one member set, is the actual next step:

| Layer | What it composes | Its members' `kind` | Parallel |
|---|---|---|---|
| Cluster infrastructure (Kubernetes **Node**s) | the machines joining the K8s cluster | `vm` (the common case) or `host` (bare-metal K8s node) — both already-decided atomic kinds | Structurally identical to `cluster`'s composition of `host`s — same shape, different orchestrator (kubelet vs. pmxcfs), so this row belongs *in the composite table above*, not as a bespoke design |
| Workload (a **Pod**) | the containers a Pod groups together | `oci` — a Pod's containers are OCI containers by the Kubernetes runtime spec (containerd/CRI-O) | Not a new pattern either: this is `oci`'s existing nesting question (row above), just with a K8s Node as the substrate instead of a bare `vm`/`lxc`/`host` |

Neither layer needs a new atomic kind. What's actually undecided is **naming and scoping**: does `kubernetes` become the infrastructure row (parallel entry in the composite table, alongside `cluster`), with the workload/Pod case handled entirely by `oci`'s own open composability question — or does it need to be two separately-named values from the start? This is now a real, scoped design question rather than an open-ended "pods? nodes? both?" — see Open questions.

**Explicitly rejected:** `shim` was raised again as a candidate `kind` and rejected again, on the same grounds as §3 below — it is a state ("a step toward something else"), not a device type. No change to §3's treatment; recorded here for the trail.

### 2. Position is recorded, not encoded in the value

Two facts that Appendix A folded into its values are already recorded elsewhere, and stay there:

- **Is the Host a cluster member?** Declared in `site.json`. Not duplicated into `kind`.
- **Where is it — locally, or off-site through a tunnel?** The **zone** (ADR-014) and the **Location** (ADR-022b). The `edge` zone exists for exactly the satellite case.

### 3. `realized` is a state, not a value

Whether a workload's storage or service is actually built is orthogonal to what it is. ADR-012's `shim` is `realized: false`. Expressing it as a peer value makes "placed on a host, not yet built" inexpressible.

The full retirement mapping (all six Appendix A terms against both this ADR's `kind` and ADR-022a D6 together) lives on the spine — [ADR-022 §Mapping](<ADR-022 - Workload Ontology.md#mapping--appendix-a-retires-cleanly>) — since it draws on both ribs plus `site.json` and the zone, not on this rib alone.

## Consequences

### Positive
- `external` stops being a hosting fact, a management claim and a placement state at once.
- `kind` gets one definition instead of two contradictory ones, with every decided value tied to an external or sibling-ADR normative source rather than invented.
- Three of the four original open candidates ratify cleanly onto existing sources without inventing new vocabulary: `device` reuses a term already in this ADR family's citation table; the PBS case needed no new value at all; `oci` is named after its own standard and evidenced in a live module. Only `kubernetes` remains open, and now for a well-scoped reason (it's two composites, not one) rather than an open-ended one.
- ADR-012 Appendix A retires jointly with ADR-022a D6; ADR-012 keeps only backup.
- This document now owns exactly one question, matching its rib in ADR-022's spine — no overlap with ADR-022a's charter.
- **Validated against every real module in both the core and Community repos, not just designed in the abstract**: every module found maps cleanly to a decided value except the two flagged gaps above (Open questions 1–2). `device` alone accounts for 57% of the Community catalog — without it, over half that catalog would have no home in the taxonomy at all.

### Negative / costs
- A schema-value migration across the seven files ADR-022c names in the core repo carrying `external-host`, **plus an eighth in the Community repo** (`AndreasJe/mailserver-hub/satellite-smtp-relay-additions/schemas/satellite-fields.json`, found by inspection — the retirement's blast radius crosses repo boundaries) — now also touching every `kind: guest` site, since `guest` no longer exists as a value.
- `kind`'s enumeration still has one genuinely open candidate, `kubernetes` — this pass could not responsibly force-close it once decomposing it revealed two conflated composites rather than one undesigned value.
- **`kind` collides with a production field of the same name that already means something else** (Open question 1) — this is the largest open cost: it is not clear the new enumeration can ship into the existing `kind` field without breaking `module-manager list`'s discovery logic, or without a second field.
- Manager→Controller dispatch by `kind` is a direction, not a built mechanism (`module-manager` doesn't do it yet) — this ADR fixes the vocabulary it will need, not the dispatch code itself.

## Open questions

1. **`kind` already means something else in production, today — this blocks migration, not just naming.** `module-fields.json` currently defines `kind` with values `module` / `external-host`, stamped automatically by `module-manager module add` (`jq '.kind = "module"'`) as a **discovery marker** — `module-manager list`'s live logic reads `kind === "module"` to tell a deployed module config apart from other JSON in `config/`. That is a different axis from this ADR's `vm`/`lxc`/`host`/`cluster`/`device` device-type enumeration, and ADR-012's own "Open against ADR-022d" section already named the resulting tension (discovery survives via a fallback when `kind` isn't `"module"`, but the marker stops being authoritative) — recorded there, one-directionally, not here. Restated here because this ADR is where the enumeration is actually decided: either `kind` keeps `module`/`external-host` as reserved values alongside the device-type ones (which values a workload should skip when scanning `config/`?), or the object-type marker needs a field of its own before `kind`'s new values can ship. Confirmed still unresolved by inspection of live `module-fields.json` and `module-manager`.
2. **A real completeness gap: modules with no runtime footprint at all.** `src/foundation/templates` has no `vmname`, no `dependsOn: cluster:*`, no `node` — it's a pure capability-provider/catalog entry (`provides: ["nixos","debian"]`), not a workload or a device. It doesn't fit any of the six decided values, and this ADR never scoped whether `kind` applies to provides-only modules at all, or only to things with an actual runtime instance. Found by inspection; no other module in either repo has this shape, so it may be the only instance — still needs an answer.
3. **`backup:vm` naming drift — narrowed, not eliminated, by the `vm`/`lxc` split.** `backup:vm` already matches the new `kind: vm` value exactly, so no rename is needed there. It's still inexact for a `kind: lxc` workload requesting the same capability. **Recommended: leave it** — `backup:vm` is a capability name, not a restatement of `kind`; 14 modules depend on it and a rename buys nothing.
4. **Does a satellite need a `pending` phase** (host up, tunnel or storage not yet configured)? Raised in the source taxonomy, still open.
5. **`kubernetes` names two different composites, not one — decompose before naming, don't force-pick.** Sharpened in review (see the table above): a K8s cluster's Node layer is a composite of `vm`/`host` (parallel to `cluster`, same shape); a Pod is a composite of `oci` containers (an instance of `oci`'s own nesting question, below). The "one module vs. a grouping of modules" framing this was originally parked under was ambiguous about *which* grouping. Two candidate resolutions, neither chosen: (a) `kubernetes` becomes the infrastructure row only, parallel to `cluster` in the composite table, and the Pod/workload case is entirely `oci`'s concern; or (b) two separately-named values from the start. Confirmed no k8s-shaped config exists in either repo today, consistent with staying unimplemented either way.
6. **`oci`'s nesting mechanism** — the value itself is now decided (atomic table, above); how an `oci`-kind module declares its relationship to the `vm`/`lxc`/`host` it runs inside — a `dependsOn` edge, a nested config block, a separate module entirely — is not, on the same terms `cluster`'s membership mechanism is deferred (parking lot, below). `ollama-nvidia` needs this in practice today (see the table above) but currently just embeds the Docker Compose file inline, undeclared.
7. **Does OS become part of the classification for bare-metal hosts** (Debian vs. NixOS vs. Windows)? Raised, unresolved.
8. **A "degree of management" axis** (aware-of → manage-network → manage-firmware → fully-managed-like-a-standard-Debian-host) was raised as a candidate enumeration distinct from both ADR-022a D6 and this ADR's `kind` — this is where the PBS "standardized way of managing Debian machines" distinction actually lives, not in `kind` itself. **Confirmed by inspection that this axis cuts across `kind: vm`/`lxc` too, not just `host`/`device`**: `hass` (Home Assistant OS) is `kind: vm` — a normal Proxmox VM by substrate — but its config sets `imageType: img` (a raw third-party appliance image, not a TAPPaaS template) and `sshAccess: false` — TAPPaaS provisions the VM and then has no path into the guest at all; HAOS manages its own updates entirely, the same shape as the PBS case, just at the opposite end and inside a `vm` rather than a `host`. `imageType` (values `clone`/`iso`/`img`/`apt`, already in `cluster/fields.json`) plus `sshAccess`/`cloudInit` are existing schema fields this axis could build on — no new field is obviously needed, only a decision to treat them as the axis's realization. Not designed here; a future open question for this ADR or a successor.
9. **Abstraction vs. routing.** Does `kind` exist so a Manager can ask every device the *same* questions, or so it knows *which* controller-specific questions to ask? Agreed as the direction to take, no pluggable design yet. Affects how far `kind`'s enumeration needs to grow versus how much a Controller can hide.

*Moved to [ADR-022a](<ADR-022a - Administrative Domain.md>) in v0.3, as they were about D6's values, not `kind`:* where the `no-site`/`other-site`/`unknown` inventory lives, and how `unknown` is discovered.

### Parking lot — explicitly out of scope here

The `node` field's replacement by a general `depends-on` relationship (a module depends on another module that happens to be a Host, rather than naming a node) — and the fuller recursive module model this implies (hosts and the cluster itself as modules other modules depend on) — was discussed and explicitly deferred as a **3.0 change**. Today's `node` field semantics, as described in [ADR-022c](<ADR-022c - Node and Host.md>), are unaffected by this ADR. This is recorded here only as a forward pointer, not a decision; it may eventually motivate a change to `cluster`'s module boundary above, but that is future work.
