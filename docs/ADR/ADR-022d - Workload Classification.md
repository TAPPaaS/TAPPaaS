What type of device or workload a `this-site` resource is — TAPPaaS's `kind`.

---

## Context

ADR-012 Appendix A carries a six-value taxonomy — `node` · `standalone` · `satellite` · `external` · `remote` · `rogue` — marked *"companion reference, not a decision"*, destined for its own ADR. This is that ADR, together with [ADR-022a](<ADR-022a - Administrative Domain.md>) D6/D7, which now owns the "who administers it" half of the split this ADR originally proposed.

Appendix A's table is correct but flat: it answers two questions at once (who runs it, and what type it is), which is why `external` ends up spanning cases that behave differently and why `shim` sits as a peer value beside placements rather than as a state of one. [ADR-022a](<ADR-022a - Administrative Domain.md>) D6 answers the first question; this ADR answers the second.

This is urgent rather than tidy for two reasons:

1. **`kind` is already broken.** `module-fields.json` defines `kind: external-host` as *"a non-module **cluster guest**"*; `satellite-fields.json` defines the same value as *"an EXTERNAL host, **NOT** a Proxmox cluster:vm"*. Both on `main`. A satellite this Site provisions and manages is filed under a value named "external".

2. **`kind` is not just vocabulary — it is a dispatch key.** [ADR-007f](<ADR-007f - Realization.md>) already establishes Manager → Controller → Service as the built control plane: a Manager owns a domain's verb surface (`list`/`show`/`validate`/`reconcile`, …) and calls a Controller for the live I/O behind it. `kind` is the field a Manager would read to pick the right Controller — today `module-manager` does not yet do this (per ADR-007f's as-built mapping it always uses the `cluster:vm` / `network:proxy` install-service hooks regardless of `kind`), but a `proxmox-controller` already exists to be routed to for VM/LXC workloads, and nothing exists yet for a bare hardware device (2026-09-11 sync). A wrong or ambiguous `kind` is therefore not a documentation defect, it is a routing defect. Whether `kind` should let a Manager ask every device the *same* questions (full abstraction) or only enough to route to the right Controller (which then asks its own type-specific questions) is itself still open, direction agreed, mechanism not designed — see Open questions.

## Decision

### 1. `kind` answers one question: what type of device/workload is this

Asked only once [ADR-022a](<ADR-022a - Administrative Domain.md>) D6 has classified a workload as `this-site`. This is `kind` — the object-type marker [ADR-022c](<ADR-022c - Node and Host.md>) D5 defines as tooling-written, never hand-authored. v0.1 asked "what does it run on," which is the wrong question: as `kind` grows beyond VM/LXC (below), two workloads can share a substrate and still be different device types, and the substrate question is already answered elsewhere — by the Host/`node` relationship (ADR-022c), not by `kind`. `kind` answers **what class of device or workload this is**.

**Atomic vs. composite kind — two different registers, two tables, not one.** Four of the five decided values each classify *one* workload or device. `cluster` classifies a *system built from binding several `host`-kind Nodes together* — it has members, the others don't. Concatenating it into a single flat table understates that difference; it gets its own table below, sized for one row today because only one composite value is decided, with room to grow (`kubernetes`, if it's ever ratified, would join it).

**Decided values — atomic kinds** (each classifies exactly one workload or device):

| `kind` | Meaning | Module boundary | Normative anchor | Examples |
|---|---|---|---|---|
| `vm` | a virtual machine (KVM/QEMU) running on a cluster member | the VM | [DMTF Redfish](https://www.dmtf.org/standards/redfish) `SystemType: Virtual`, sub-split by Proxmox VE's own `qemu` API | `openwebui` (App VM in a Service zone) |
| `lxc` | a Linux Container (LXC) running on a cluster member | the container | Redfish `SystemType: Virtual`, sub-split by Proxmox VE's own `lxc` API | `vllm-amd` (declares `dependsOn: cluster:lxc`) |
| `host` | its own Node, manageable by TAPPaaS (SSH, checks, updates) but not a cluster guest — cluster-member or not | the host | Redfish `SystemType: Physical` | `backup` (PBS, non-cluster-member) · `tappaas1`/`tappaas2` (cluster-member Proxmox nodes — same `kind`; membership is recorded separately, §2 below) |
| `device` | reachable by IP, unmanaged beyond network configuration — TAPPaaS cannot SSH into it or run checks against it | the device itself (no VM/host distinction applies) | [ArchiMate 3.x](https://pubs.opengroup.org/architecture/archimate3-doc/ch-Technology-Layer.html) Device ("a physical IT resource with processing capability... can also be used to model virtualized hardware") — the same term ADR-022c D1 already reaches for | `alfen`, `smlight` — policy-only (`network:rules`/`network:discovery`/`network:snat`, never `cluster:vm`/`cluster:lxc`); **57% of the Community catalog fit this shape as of 2026-09-11** (12 of 21 modules audited, none `kind`-tagged today) — a point-in-time validation count, not a maintained list; the module catalog itself is the source of truth |

**Decided values — composite kinds** (a value whose module has *members*, each itself atomic-`kind`):

| `kind` | Meaning | Module boundary | Normative anchor | Examples |
|---|---|---|---|---|
| `cluster` | the Proxmox cluster itself, as a module in its own right — `site.json` stops directly enumerating cluster nodes; its members are `host`-kind Nodes | the cluster | Redfish `SystemType: Composed` ("a computer system constructed by binding resource blocks together"); ArchiMate's **Composition** relationship for the `cluster`–`host` membership itself (see below) | `src/foundation/cluster/cluster.json` — the catalog module **already exists** (`status: Production`, `provides: ["vm","lxc","ha"]`); it has simply never carried a `kind` value, same as everything else in the repo |

`cluster` and `device` are decided-now, not 3.0 items — neither requires the `node`→`depends-on` change (parking lot, below); `cluster` only needs a module file, `device` only needs a module registered against something TAPPaaS can't inspect as a Node.

**Why `cluster` is a composite.** ArchiMate's **Composition** relationship — exclusive membership, a node belongs to exactly one cluster — is the correct relation for `cluster`–`host` (Aggregation would permit sharing, which cluster membership doesn't). DMTF Redfish's **Composability** model — a `ResourceBlock` bound via the Composition Service into a `ComposedNode` — is the same shape, and is what the table's `SystemType: Composed` citation actually names. (`kubernetes`'s still-open composite question, Proposed below, would reuse this same shape.)

Composite kinds are referenced the same way atomic ones already are: the `<module>:<capability>` `dependsOn`/`provides` convention ([ADR-003](<ADR-003 - Dependency management in TAPPaaS.md>)/[ADR-009](<ADR-009 - Composition Meta-Model.md>)). `cluster.json` provides `vm`/`lxc`/`ha`; `openwebui.json` and `vllm-amd.json` depend on `cluster:vm`/`cluster:lxc` respectively (verified, live on `main`) — the capability suffix already matches `kind`'s own value names. `dependsOn: cluster:vm` is the module-authored request; `kind: vm` is the tooling-stamped result ([ADR-022c](<ADR-022c - Node and Host.md>) D5) — request and result, not duplicate data.

**MECE check**, five boundaries, each a different axis:

- **`vm` vs `lxc`** — which Proxmox API manages them (`qemu` vs `lxc`).
- **`host` vs `device`** — manageability, not physicality. A `host` can be virtual (the ADR-010 satellite); what makes it `host` is that TAPPaaS can SSH in and manage it, not whether it's physical.
- **`host` vs `cluster`** — atomic vs. composite; disjoint by construction.
- **`device` vs everything else** — never runs a TAPPaaS-managed workload, so it can't collide with anything that does.
- **`device` vs ADR-008's network-plane hardware** — different domain. Switches/APs are `switch-controller`/`ap-controller`'s (ADR-007f, ADR-008), never `kind`-classified at all; a UniFi controller itself is `kind: vm` (it's the software, not the hardware it controls). Confirmed by inspection: no module blurs this today.

Proof the split lands on the right axis: `deconz` (`kind: vm` — USB passthrough to a physical Zigbee dongle) and `smlight` (`kind: device` — a network-attached Zigbee coordinator) are the same application domain, correctly different `kind`s — the taxonomy asks whether there's TAPPaaS-managed compute, not what the module does.

`guest` (v0.1–v0.4) is retired: too generic to distinguish `vm` from `lxc`, a distinction Manager dispatch (Context §2) needs operationally. `external-host` is retired: it named the administrative aspect (now [ADR-022a](<ADR-022a - Administrative Domain.md>) D6) while defining the hosting one — the source of its two contradictory schema definitions.

**Proposed — not decided:**

| Candidate | What it would cover | Status |
|---|---|---|
| `oci` | an OCI application container as its **own module-catalog entry** — a module whose `kind` is the container itself, no enclosing `vm`/`lxc`/`host` module wrapping it | **Not decided — reconsidered on review, downgraded from an earlier draft's "decided."** Podman/OCI containers are common inside TAPPaaS `vm`/`lxc` modules — `openwebui`, `litellm`, and `ollama-nvidia` all run one — but in every real case the container is §2's "what runs internally," invisible to `kind`: the module TAPPaaS tracks is the enclosing VM or LXC, never the container. No module in either repo is *itself* `kind`-classified as a bare container. `oci` would only become real if TAPPaaS ever wants to track a container as a module in its own right, bypassing a `vm`/`lxc` wrapper entirely — not evidenced anywhere today. If it is needed, [OCI Image & Runtime Specifications](https://opencontainers.org/) remains the right anchor, and the name stays distinguished from `lxc` on the same grounds as before (LXC: system container, own init; OCI: application container, one process) |

`kubernetes` is not one open candidate either, it's a name that turns out to cover **two different composites**, conflated exactly the way `external-host` once conflated two meanings in one value — decomposing this, not force-picking one member set, is the actual next step:

| Layer | What it composes | Its members' `kind` | Confidence |
|---|---|---|---|
| Cluster infrastructure (Kubernetes **Node**s) | the machines joining the K8s cluster | `vm` (the common case) or `host` (bare-metal K8s node) — both already-decided atomic kinds. **No new `k8s-node` value — ratified, not a candidate.** A K8s Node is a `vm`/`host` that also has a K8s-cluster-membership relationship, exactly the shape §2 already settled for Proxmox ("Is the Host a cluster member? Declared in `site.json`. Not duplicated into `kind`.") — reuse that principle rather than reinvent it for a second orchestrator. Structurally identical to `cluster`'s composition of `host`s (same shape, different orchestrator — kubelet vs. pmxcfs), so this row belongs *in the composite table above*, not as a bespoke design | High — reuses an already-decided principle |
| Workload (multiple containers grouped together) | the containers a group runs as a unit | `oci` members, if `oci` itself is ever ratified as its own module-catalog entry (above) | **Candidate only, doubly unratified — `oci` itself isn't decided, and no multi-container instance exists either way.** Not Kubernetes-specific: were it needed, two real standards already exist to reuse rather than reinvent — Kubernetes' own **Pod** (when running under a `kubernetes` composite) or the open **[Compose Specification](https://github.com/compose-spec/compose-spec)** (compose-spec.io — the standard `docker-compose.yml` itself implements, no Kubernetes required; `ollama-nvidia`'s own compose file uses this format today, single-service) | Low — no TAPPaaS instance either layer, mark candidate |

The infrastructure row is decided in shape (no new atomic kind, ever — the pattern is closed). What's still open is **naming and scoping `kubernetes` itself**: does it become the infrastructure row's name in the composite table, parallel to `cluster`, with the workload/multi-container case handled entirely by `oci`'s own (still open) existence question — or does `kubernetes` need to be two separately-named values from the start? This is now a real, scoped design question rather than an open-ended "pods? nodes? both?" — see Open questions.

**Explicitly rejected:** `shim` was raised again as a candidate `kind` and rejected again, on the same grounds as §3 below — it is a state ("a step toward something else"), not a device type. No change to §3's treatment; recorded here for the trail.

### 2. Position is recorded, not encoded in the value

Two facts that Appendix A folded into its values are already recorded elsewhere, and stay there:

- **Is the Host a cluster member?** Declared in `site.json`. Not duplicated into `kind`.
- **Where is it — locally, or off-site through a tunnel?** The **zone** (ADR-014) and the **Location** (ADR-022b). The `edge` zone exists for exactly the satellite case.
- **What does the guest run internally?** Never `kind`. `kind` classifies the module-catalog boundary — the unit TAPPaaS provisions, clones, backs up and reconciles as one thing — not the guest OS's own architecture. Checked by inspection: `litellm.nix` runs PostgreSQL and Redis as native NixOS services *and* the LiteLLM proxy itself as a genuine OCI container (`virtualisation.oci-containers.containers.litellm`, image `docker.io/litellm/litellm:...`, via podman) — three distinguishable components, one `kind: vm` module. `openwebui.nix` does the same (`podman run docker.io/openwebui/open-webui:...`, wrapped in a plain systemd unit rather than the higher-level NixOS option, same effect). Neither is exceptional — podman/OCI-inside-a-NixOS-VM is the *normal* way TAPPaaS app modules package third-party software, not a special case. `kind` staying at `vm` regardless is not an oversight, it's this bullet: internal composition is Nix's problem, not the module catalog's, for the same reason a cluster-membership fact lives in `site.json` and not in `kind` — recording it a second time, in a second place, is exactly the drift this ADR exists to stop.

### 3. `realized` is a state, not a value

Whether a workload's storage or service is actually built is orthogonal to what it is. ADR-012's `shim` is `realized: false`. Expressing it as a peer value makes "placed on a host, not yet built" inexpressible.

The full retirement mapping (all six Appendix A terms against both this ADR's `kind` and ADR-022a D6 together) lives on the spine — [ADR-022 §Mapping](<ADR-022 - Workload Ontology.md#mapping--appendix-a-retires-cleanly>) — since it draws on both ribs plus `site.json` and the zone, not on this rib alone.

## Consequences

### Positive
- `external` stops being a hosting fact, a management claim and a placement state at once.
- `kind` gets one definition instead of two contradictory ones, with every decided value tied to an external or sibling-ADR normative source rather than invented.
- Two of the four original open candidates ratify cleanly onto existing sources without inventing new vocabulary: `device` reuses a term already in this ADR family's citation table; the PBS case needed no new value at all. `oci` and `kubernetes` remain open, but each for a well-scoped reason now (Open questions 5–6) rather than an open-ended one.
- ADR-012 Appendix A retires jointly with ADR-022a D6; ADR-012 keeps only backup.
- This document now owns exactly one question, matching its rib in ADR-022's spine — no overlap with ADR-022a's charter.
- **Validated against every real module in both the core and Community repos, not just designed in the abstract**: every module found maps cleanly to a decided value except the two flagged gaps above (Open questions 1–2). `device` alone accounts for 57% of the Community catalog — without it, over half that catalog would have no home in the taxonomy at all.

### Negative / costs
- A schema-value migration across the seven files ADR-022c names in the core repo carrying `external-host`, **plus an eighth in the Community repo** (`AndreasJe/mailserver-hub/satellite-smtp-relay-additions/schemas/satellite-fields.json`, found by inspection — the retirement's blast radius crosses repo boundaries) — now also touching every `kind: guest` site, since `guest` no longer exists as a value.
- `kind`'s enumeration still has two genuinely open candidates, `oci` and `kubernetes` (Open questions 5–6) — this pass could not responsibly force-close either.
- **`kind` collides with a production field of the same name that already means something else** (Open question 1) — this is the largest open cost: it is not clear the new enumeration can ship into the existing `kind` field without breaking `module-manager list`'s discovery logic, or without a second field.
- Manager→Controller dispatch by `kind` is a direction, not a built mechanism (`module-manager` doesn't do it yet) — this ADR fixes the vocabulary it will need, not the dispatch code itself.

## Open questions

1. **`kind` already means something else in production, today — this blocks migration, not just naming.** `module-fields.json` currently defines `kind` with values `module` / `external-host`, stamped automatically by `module-manager module add` (`jq '.kind = "module"'`) as a **discovery marker** — `module-manager list`'s live logic reads `kind === "module"` to tell a deployed module config apart from other JSON in `config/`. That is a different axis from this ADR's `vm`/`lxc`/`host`/`cluster`/`device` device-type enumeration, and ADR-012's own "Open against ADR-022d" section already named the resulting tension (discovery survives via a fallback when `kind` isn't `"module"`, but the marker stops being authoritative) — recorded there, one-directionally, not here. Restated here because this ADR is where the enumeration is actually decided: either `kind` keeps `module`/`external-host` as reserved values alongside the device-type ones (which values a workload should skip when scanning `config/`?), or the object-type marker needs a field of its own before `kind`'s new values can ship. Confirmed still unresolved by inspection of live `module-fields.json` and `module-manager`.
2. **A real completeness gap: modules with no runtime footprint at all.** `src/foundation/templates` has no `vmname`, no `dependsOn: cluster:*`, no `node` — it's a pure capability-provider/catalog entry (`provides: ["nixos","debian"]`), not a workload or a device. It doesn't fit any of the five decided values, and this ADR never scoped whether `kind` applies to provides-only modules at all, or only to things with an actual runtime instance. Found by inspection; no other module in either repo has this shape, so it may be the only instance — still needs an answer.
3. **`backup:vm` naming drift — narrowed, not eliminated, by the `vm`/`lxc` split.** `backup:vm` already matches the new `kind: vm` value exactly, so no rename is needed there. It's still inexact for a `kind: lxc` workload requesting the same capability. **Recommended: leave it** — `backup:vm` is a capability name, not a restatement of `kind`; 14 modules depend on it and a rename buys nothing.
4. **Does a satellite need a `pending` phase** (host up, tunnel or storage not yet configured)? Raised in the source taxonomy, still open.
5. **`kubernetes`** — decomposed into two composites in the Proposed table above, not force-picked. Infrastructure layer: ratified reuse of `vm`/`host`, no new `k8s-node` value. Workload layer: candidate only, blocked on `oci`'s own open question (6). What remains is naming/scoping `kubernetes` itself — the infrastructure row's name in the composite table, or two separately-named values from the start.
6. **`oci`** — reconsidered in the Proposed table above: every real podman/OCI usage found is guest-internal detail (§2), never itself module-tracked. Whether it needs to exist as a `kind` value at all — not just how it would nest — is the open part.
7. **Does OS become part of the classification for bare-metal hosts** (Debian vs. NixOS vs. Windows)? Raised, unresolved.
8. **A "degree of management" axis** (aware-of → manage-network → manage-firmware → fully-managed-like-a-standard-Debian-host) was raised as a candidate enumeration distinct from both ADR-022a D6 and this ADR's `kind` — this is where the PBS "standardized way of managing Debian machines" distinction actually lives, not in `kind` itself. **Confirmed by inspection that this axis cuts across `kind: vm`/`lxc` too, not just `host`/`device`**: `hass` (Home Assistant OS) is `kind: vm` — a normal Proxmox VM by substrate — but its config sets `imageType: img` (a raw third-party appliance image, not a TAPPaaS template) and `sshAccess: false` — TAPPaaS provisions the VM and then has no path into the guest at all; HAOS manages its own updates entirely, the same shape as the PBS case, just at the opposite end and inside a `vm` rather than a `host`. `imageType` (values `clone`/`iso`/`img`/`apt`, already in `cluster/fields.json`) plus `sshAccess`/`cloudInit` are existing schema fields this axis could build on — no new field is obviously needed, only a decision to treat them as the axis's realization. Not designed here; a future open question for this ADR or a successor.
9. **Abstraction vs. routing.** Does `kind` exist so a Manager can ask every device the *same* questions, or so it knows *which* controller-specific questions to ask? Agreed as the direction to take, no pluggable design yet. Affects how far `kind`'s enumeration needs to grow versus how much a Controller can hide.

*Moved to [ADR-022a](<ADR-022a - Administrative Domain.md>) in v0.3, as they were about D6's values, not `kind`:* where the `no-site`/`other-site`/`unknown` inventory lives, and how `unknown` is discovered.

### Parking lot — explicitly out of scope here

The `node` field's replacement by a general `depends-on` relationship (a module depends on another module that happens to be a Host, rather than naming a node) — and the fuller recursive module model this implies (hosts and the cluster itself as modules other modules depend on) — was discussed and explicitly deferred as a **3.0 change**. Today's `node` field semantics, as described in [ADR-022c](<ADR-022c - Node and Host.md>), are unaffected by this ADR. This is recorded here only as a forward pointer, not a decision; it may eventually motivate a change to `cluster`'s module boundary above, but that is future work.

- [ ] Resolved: whether `kind`'s new values coexist with `module-fields.json`'s existing `module`/`external-host` discovery-marker use, or the object-type marker gets its own field (Open question 1)
- [ ] Resolved: whether `kind` applies to provides-only, no-runtime modules like `templates` (Open question 2)
- [ ] Each decided value's normative anchor recorded in `GLOSSARY.md` §A alongside the value itself
- [ ] Manager→Controller dispatch-by-`kind` rationale documented (Context §2), citing ADR-007f, with today's as-built gap noted (not yet implemented in `module-manager`)
- [ ] `kubernetes` recorded as open, not decided, decomposed into its two conflated composites rather than left as an open-ended question; `oci` recorded as open at the more basic level of whether it needs to exist as a `kind` value at all, given no module anywhere is module-tracked as a bare container
