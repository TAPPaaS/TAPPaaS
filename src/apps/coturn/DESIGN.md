# coturn — Design notes

## Architecture

```
Client A (NAT) ─[UDP 3478]─▶ coturn (DMZ) ─[UDP 3478]─▶ Client B (NAT) / Janus (HPB)
                                  ▲
                  Nextcloud (srv) │ issues per-call credentials (shared HMAC secret)
                  HPB / Janus     │ TURN REST API → same secret
```

- Custom systemd `coturn` service (not the NixOS `services.coturn` module): secrets are
  loaded at runtime from `/etc/secrets/coturn.env` and the config is written to
  `/run/coturn/turnserver.conf` at each service start, so secrets never appear in the
  Nix store.
- No reverse proxy, no database, no Redis. Exposed ports: TCP 22 (SSH), TCP/UDP 3478
  (TURN/STUN), UDP 49152-50151 (relay range). The VM sits in the `dmz` zone.
- The relay range is 1,000 ports: one per allocation, so about 1,000 relayed legs at once.
  Widen it in `coturn.json` and `coturn.nix` together.
- coturn tracks `pkgs.coturn` (nixpkgs) via the `versions` block in `coturn.nix`;
  `appVersion` in `coturn.json` mirrors the pinned package version.
- 2 vCPU: with the HPB's Janus SFU every participant Janus cannot reach directly relays
  through coturn, so the relay carries more legs than in the mesh days.

## One name in every horizon (`publicDomain`)

A TURN host is handed to every client by Talk, so it has to resolve everywhere: a phone on
mobile data cannot resolve `coturn.dmz.internal`, and a laptop inside the site that
resolves the public name to the WAN IP hairpins into a NAT that does not reflect. Hence:

- `publicDomain` (module-fields.json), defaulting to `turn.<site domain>` and persisted into
  the deployed config on first converge so every reader agrees.
- A split-horizon host override on the site resolver, `publicDomain → coturn VM address`,
  registered by `public-name.sh` (install and update). It deliberately does **not** reuse
  `network:proxy`'s gateway derivation: TURN is not HTTP, media must reach the relay itself.
- The public A record → WAN IP is the operator's one manual step.
- `home` reaches the relay directly through a declared `ingress` pinhole (the zone lacks `dmz`
  in `access-to`); `dmz.pinhole-allowed-from` must list it. A site with further client zones
  declares the same pinhole for each.

## WAN exposure — declared, not a reminder

`coturn.json` declares `network:nat` `natRules` for 3478 TCP/UDP and the 49152-50151 UDP
relay range; the service creates rdr-pass rules on OPNsense. Earlier the installer only
printed a reminder, and a site ran for months with zero port-forwards while Talk's admin
check stayed green — the check probes 3478 only, and nothing probes the relay range.
coturn is the first `natRules` consumer with a **port range**; the range's target port is the
range start (OPNsense semantics).

## Secret planes

- Runtime: `/etc/secrets/coturn.env` on the coturn VM — `COTURN_SECRET` (64-char hex) is
  auto-generated by NixOS on first boot; `COTURN_EXTERNAL_IP` is set by `install.sh`
  (auto-detected from the VM) or manually.
- Management: `/home/tappaas/secrets/coturn.env` on tappaas-cicd — `install.sh` (and the
  `coturn:turn` service, for each consumer) read the secret from the VM and upsert it here
  (`pre-install.sh` creates the file with mode 600 before dependency installers run).
  Consumers with no SSH path to the coturn VM (Nextcloud Talk, `nextcloud-hpb`) read it here.

## Connector ownership (ADR-COM-0002)

- **`talk` connector** — `config["nextcloud:fileservice"].connector = "talk"` on this module.
  Nextcloud's `services/fileservice/update-service.sh` reads `COTURN_SECRET` from the
  management plane and `publicDomain` from coturn's deployed config, writes
  `/etc/secrets/talk.env` on the Nextcloud VM and restarts
  `nextcloud-configure-talk-turn.service`, which runs `occ talk:stun:add` / `talk:turn:add`.
  Re-applied on every converge of coturn (its dependency services) and of Nextcloud.
  Until 0.3.0 this declaration was a no-op: only the HPB install registered TURN, as a side
  effect, so a coturn-only site had no relay.
- **`coturn:turn` service** (provided) — for each consumer: publishes the secret to the
  management plane and stamps `turnHost` (`services/turn/fields.json`) into the consumer's
  deployed config, so the consumer's `.nix` advertises the same name (`nextcloud-hpb.nix`
  reads it from its companion JSON for the signaling server's `turn.servers` and for Janus).

coturn does only its own layer; there is no cross-VM SSH push from this module.

## Deploy notes and known limitations

- The shared TURN secret is published to the management plane and consumed by
  Nextcloud/HPB (the connector is owned by Nextcloud, ADR-COM-0002).
- No `turns:` (TLS) listener: the site's single WAN IP serves 443 through Caddy, so the usual
  "TURN on 443" fallback for locked-down guest networks is not available here; a 5349 listener
  needs a certificate distributed to the VM and is a follow-up.
- Verify with a real off-network call, not the Talk admin checkmark (see INSTALL.md).

## Superseded install-time customisation

Earlier docs suggested per-flag overrides (`install-module.sh coturn --node tappaas2
--vmid 399`, flags `--node`, `--zone0`, `--vmid`). The current convention is to copy
`coturn.json` to `/home/tappaas/config` and edit it before installing.
